# 08. API設計 — エンドポイントとエラー処理

フロントとサーバーの間の「会話のルール」を決める。フェーズ1 で UI（[04](./04-ui-and-components.md)）がフロント内の境界を決めたのに対し、ここではフロントとサーバーの境界を決める。

## 1. 設計方針

- **REST 風**：「リソース（todos）に対して HTTP メソッドで操作を表す」形にする。URL が「何に対する操作か」、メソッドが「どんな操作か」を表すので、エンドポイントの意味が名前から読み取れる
- すべて `/api` 配下・JSON でやり取りする
- ページング・認証・API バージョニングはやらない（現在の要件にない。必要になったら足す）

## 2. エンドポイント一覧

`useTodos` の4操作（[03](./03-data-model.md) §2）と 1:1 に対応する4本。

| メソッド | パス             | やること                   | 対応要件  |
| -------- | ---------------- | -------------------------- | --------- |
| GET      | `/api/todos`     | 一覧取得（追加順）         | F-2       |
| POST     | `/api/todos`     | 追加                       | F-1       |
| PATCH    | `/api/todos/:id` | 完了切替・編集（部分更新） | F-3 / F-5 |
| DELETE   | `/api/todos/:id` | 削除                       | F-4       |

`:id` は URL の一部としてタスクの `id` を埋め込む書き方（例：`/api/todos/3f2504e0-...`）。

**更新を PATCH 1本にまとめる理由**：PATCH は「送った項目だけを書き換える」部分更新のメソッド。完了切替は `{ completed }` だけ、編集は `{ title }` だけを送ればよく、`useTodos` の `toggleTodo` / `editTodo` とそのまま対応する。PUT（全項目を送って丸ごと置き換え）にしないのは、操作の意図がリクエストの中身から読み取れる方が分かりやすいため。

## 3. 各エンドポイントの詳細

### GET /api/todos — 一覧取得

- レスポンス：`200` + `Todo[]`（追加順。0件なら `[]`）

```json
[{ "id": "3f2504e0-...", "title": "牛乳を買う", "completed": false }]
```

### POST /api/todos — 追加

- リクエスト：`{ "title": "牛乳を買う" }`（`id` は送らない。サーバーが採番する）
- レスポンス：`201` + 作成された `Todo`（`completed` は `false`）
- エラー：`400`（`title` が空文字・空白のみ・文字列でない・ボディが JSON でない）

`201 Created` は「作成に成功した」専用の成功コード。作成された `Todo` を返すのは、フロントがサーバー採番の `id` を知る必要があるため。

### PATCH /api/todos/:id — 完了切替・編集

- リクエスト：`{ "title"?: string, "completed"?: boolean }`（少なくとも一方は必須）
- レスポンス：`200` + 更新後の `Todo`
- エラー：`400`（`title` が空文字・型違い・両方とも未指定）／`404`（`:id` のタスクが存在しない）

### DELETE /api/todos/:id — 削除

- レスポンス：`204`（ボディなし。「成功したが返すものはない」の意味）
- エラー：`404`（`:id` のタスクが存在しない）

## 4. エラー形式

失敗時のレスポンスボディは、どのエンドポイントでも次の1形式に統一する。

```json
{ "error": "title を入力してください" }
```

形式を1つに揃えると、フロントのエラー処理が1通りの書き方で済む。

| ステータス | 意味                   | 起きる場面                                                       |
| ---------- | ---------------------- | ---------------------------------------------------------------- |
| `400`      | リクエストの中身が不正 | `title` が空文字・型違い、ボディが JSON でない                   |
| `404`      | 対象が見つからない     | PATCH / DELETE で指定した `id` のタスクが存在しない              |
| `500`      | サーバー側の想定外     | バグや D1 の障害など。Hono の `app.onError` でまとめて拾って返す |

## 5. バリデーション（入力チェック）

**zod などのライブラリは入れず、手書きで検査する**。検査対象は `title`（文字列かつ、前後の空白を除いて1文字以上）と `completed`（boolean）の2つだけで、ライブラリを学ぶコストの方が高くつく。`unknown` 型で受けて型ガード（`typeof` 等での絞り込み）で確かめる書き方は、それ自体が TypeScript の良い学習材料になる。置き場所は `src/server/routes/todos.ts` のハンドラ冒頭（共通化したければ同ファイル内の小さな関数で十分）。

**フロント側の空文字チェック（STEP 3・5 で実装済み）も残す**。二重チェックになるが、役割が違う。

| 場所     | 役割                                                                                                  |
| -------- | ----------------------------------------------------------------------------------------------------- |
| フロント | **即時フィードバック**。サーバーに聞かなくてもその場で弾けて、体験が良い                              |
| サーバー | **最後の砦**。フロントを経由しないリクエスト（curl 等）も来るため、データを守るのは常にサーバーの責任 |

## まとめ

- エンドポイントは4本：GET / POST `/api/todos`、PATCH / DELETE `/api/todos/:id`
- 更新は **PATCH 1本の部分更新**。`useTodos` の操作と 1:1 に対応する
- `id` はサーバー採番なので、POST は `title` だけ送る
- エラーは常に `{ "error": "..." }` の1形式。400 / 404 / 500 を使い分ける
- バリデーションは手書き。**フロントは即時フィードバック、サーバーは最後の砦**で二重に守る
