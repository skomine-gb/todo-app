# テストの書き方（意味のあるテストとは）

> これは **提出しない個人用のメモ** です。STEP11 のコードレビュー（PR #26）で受けた「意味のあるテストとは何か」という指摘を深掘りして学んだことをまとめています。
> 用語の基礎（DI・fake実装など）は [学習メモ.md](./学習メモ.md) の「HTTP通信・DIまわり」を参照。

---

## 意味のあるテストとは

テストの本質は「壊れたら教えてくれる見張り番」。いまの正しさの確認は半分で、本当の価値は**未来の変更で何かを壊したとき、落ちて教えてくれる**こと。そこから逆算すると、テストの価値を測る問いはこれ：

> **このテストが落ちたとき、何が壊れたことを意味するか？**

- 「自分が書いたロジックが壊れた」なら意味がある
- 「組み込みAPIやライブラリが壊れた」しかありえないなら無意味（`Response` や `JSON.stringify` はランタイム側が動作保証済みで、そもそもほぼ落ちない）

落ちるべきときに落ちないテストは、絶対に鳴らない火災報知器。実行時間を食い、「何か大事なものを守っている」と読む人に誤解させる分、無い方がましですらある。

## 「自分のコード」と「借り物のコード」を区別する

- **自分が書いたコード**＝自分が決めた仕様（「URLは `/api/todos`」「失敗したら汎用エラーを投げる」「POSTのときはJSONヘッダーを付ける」）。自分が書き間違えるかもしれないし、将来の変更で壊れるかもしれない → **見張る価値がある**
- **借り物のコード**＝`fetch`・`Response`・`JSON.stringify` などの組み込みAPI。提供元が動作保証している → 自分のテストで見張る必要はない

expect を書いたら「これは誰の仕事を確認している？」と自問する。答えが「ブラウザ」「ライブラリ」なら、そのexpectは自分のコードの何も守っていない。

## 実例：`fetchTodos` の成功テストが「無意味」と指摘された（STEP11のレビュー指摘）

修正前のテストはこうだった：

```ts
vi.stubGlobal("fetch", vi.fn().mockResolvedValue(jsonResponse(todos)));
await expect(todoApi.fetchTodos()).resolves.toEqual(todos);
```

データの流れを追うと「`todos` を `JSON.stringify` で文字列化 → `new Response` に詰める（テスト側）→ `res.json()` で取り出す（実装側）→ 元の `todos` と一致するか確認」。つまり**組み込みAPIの往復（梱包して開封したら元に戻る）を確認しているだけ**で、自分が書いた判断（URLの指定・エラー判定）は合否に一切影響していなかった。

見張り番の性能を測る思考実験：「わざとバグを入れたら、このテストは落ちるか？」。実装のURLを `/api/todosss` にタイポしても、このテストは**通ってしまう**（モックのfetchは何を渡されても同じ返事を返すから）。本番なら全機能が死ぬ重大バグを検知できない＝無意味。

対応：「自分が決めたこと」に expect を向け直した。

```ts
expect(fetchMock).toHaveBeenCalledWith("/api/todos", undefined);
```

「正しいURLで fetch を呼んだか」は自分のロジックなので、URLをタイポすればテストが落ちるようになった。**「消す」のではなく「検証対象を自分のロジックに向け直す」ことでテストが生き残った**のがポイント。

## 実例：`todoApi.ts` 自身も fetch をDIする（`createTodoApi`）

上の「呼ばれ方の検証」をするには fetch の呼ばれ方を覗く必要があるが、そのために `vi.stubGlobal`（グローバルの fetch を丸ごと差し替え）を使うのはNG。グローバルは全テスト共有の場所（アパートの共用廊下に私物を置くようなもの）で、①片付け（`vi.unstubAllGlobals()`）を1回忘れると無関係なテストに漏れて原因究明困難な失敗を生む、②テストの依存が暗黙になる。

対応：デフォルト引数によるDI。

```ts
export function createTodoApi(fetchImpl: typeof fetch = fetch): TodoApi { ... }
export const todoApi: TodoApi = createTodoApi(); // 本番用（引数省略＝本物のfetch）
```

- 本番：`createTodoApi()` → デフォルト値の本物 `fetch` が使われ、アプリの動きは変わらない
- テスト：`createTodoApi(fetchMock)` → ローカル変数を手渡すだけ。グローバル無傷・後片付け不要・呼ばれ方も自然に検証できる

**グローバルモック回避と意味のある検証が、DIという1つの設計変更で同時に手に入った**。「モックがつらい・グローバルを触るしかない」と感じたら、実装側の依存の持ち方（内部で勝手に掴んでいないか）を疑う。

## `vi.fn().mockResolvedValue(...)` の読み方

```ts
const fetchMock = vi.fn().mockResolvedValue(jsonResponse(todos));
```

3つの部品でできている：

1. **`vi.fn()`**：モック関数（偽関数）を作る。特別な能力は**呼ばれた履歴（回数・引数）を全部記録する**こと。通話録音機能付きの電話のイメージ。だから後で `expect(fetchMock).toHaveBeenCalledWith(...)`（「この引数で呼ばれた記録ある？」）と聞ける
2. **`.mockResolvedValue(X)`**：「呼ばれたら `X` で解決される **Promise** を返せ」という設定。本物の `fetch` が非同期（Promiseを返す）だから、代役も同じ型で振る舞う必要がある。仲間：`.mockReturnValue`（同期の返り値）／`.mockRejectedValue`（失敗するPromise＝失敗する通信の再現）
3. **`jsonResponse(todos)`**：返事の中身。「200 OK・ボディは todos のJSON」という本物そっくりの `Response` を手作りするテスト用ヘルパー

全体で「**どんな引数で呼ばれても『todos入りの成功レスポンス』を返し、かつ呼ばれ方を全部記録する、偽のfetch**」。「どんな引数でも同じ返事」だからこそ、返り値の検証だけではURLタイポを検知できず、記録の検証（`toHaveBeenCalledWith`）が必須になる——と上の実例につながる。
