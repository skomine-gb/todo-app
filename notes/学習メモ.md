## 設計まわり

### 設計とは

コードを書き始める前に「何を・どういう形で作るか」を先に決めて、言葉や図にしておくこと。家を建てる前の図面と同じ。迷い・手戻り・抜け漏れを減らせる。完璧な正解を出す作業ではなく「今わかる範囲でいったん決める」作業。あとで変えてよい。

### 要件定義

「このアプリは何ができて、何はやらないか」を作る前にはっきり決めること。設計の一番最初にやる、一番大事な作業。ここがブレると後がすべてブレる。→ [docs/01-requirements.md](../docs/01-requirements.md)

### スコープ

作る範囲の線引き。「作るもの」と同じくらい「作らないもの／次フェーズ」を明示するのが大事。決めないと機能が無限に増えて完成しない。

### 機能要件

「アプリが何をできるか」という動きの決めごと（F-1〜F-5）。あとで「実装できたか」の確認リストにそのまま使える。

### 非機能要件

「何ができるか」ではなく「どういう性質・条件で動くか」の決めごと。保存先・対応環境・性能・見た目など。→ [docs/01-requirements.md](../docs/01-requirements.md)

### アーキテクチャ

アプリ全体の大きな組み立て方・骨組み。細かいコードの前に全体像を決める。→ [docs/02-architecture.md](../docs/02-architecture.md)

## React まわり

### 状態（state / ステート）

アプリが今持っているデータの現在の中身。このアプリの状態は「タスク一覧」だけ。
Reactの基本ルール：**状態が変わる → 画面が自動で描き直される**。だから画面を直接書き換えず「状態を変える」だけでよい。→ [docs/02-architecture.md](../docs/02-architecture.md)

### useState

Reactに最初から付いている、状態を持つための仕組み。小さいアプリはこれで十分（Reduxなどの大きなライブラリは不要）。

### カスタムフック

状態まわりの処理を自分でまとめて名前を付け、使い回せるようにしたもの。今回は「タスク一覧を持ち、変わったらlocalStorageに保存する」処理を `useTodos` という名前でまとめる。→ [docs/05-directory-and-steps.md](../docs/05-directory-and-steps.md)

### コンポーネント

画面を作るための「部品」。レゴブロックのように組み合わせて画面を作る。1つの部品は1つの仕事だけを持たせる（＝単一責任）と、読みやすく直しやすい。→ [docs/04-ui-and-components.md](../docs/04-ui-and-components.md)

### props（プロップス）

親の部品から子の部品へ、データや処理を渡す仕組み。
原則：**データは上から下へ（props）／操作は下から上へ（渡された処理を呼ぶ）**。状態を持つのは一番上（App）だけにすると、今どんなデータかを1か所見れば分かる。

### ワイヤーフレーム

色や飾りを付ける前の、配置だけを決めた画面の下書き。

## メモ化・再レンダリングまわり

### 再レンダリング（re-render）

Reactのコンポーネントが、状態(state)やpropsが変わるたびに関数を再度呼び出して画面の中身を作り直すこと。「状態が変わる→画面が自動で描き直される」（→状態の項目参照）の「描き直す」部分の実体。関係ない箇所まで無駄に何度も起きると、アプリが重くなる原因になる。

### useCallback

関数の「参照（同一性）」を再レンダリングをまたいで保つためのフック。**関数の中身が実行されるのを止めるものではない**。効果があるのは、その関数を`React.memo`で包まれた子コンポーネントにpropsとして渡している時、または`useEffect`等の依存配列に入れている時だけ。渡す先が素のDOM要素（`<button onClick={...}>`など）や、`React.memo`されていないコンポーネントの場合は、参照を安定させても誰も得をしないので効果がない。

### React.memo

コンポーネントを包んで、「親から渡されたpropsが前回と同じなら再レンダリングをスキップする」ようにする仕組み。propsに関数を渡している場合、その関数が毎回新しく作られる（＝参照が毎回変わる）と`React.memo`の比較が常に「変わった」判定になり意味をなさなくなる。だから`React.memo`はしばしば`useCallback`とセットで使って初めて効果を発揮する。

`React.memo`が防げるのは「親が再レンダリングされたのに巻き込まれて自分も再レンダリングされる」ケースだけで、「自分自身の状態(`useState`)が変わったから再レンダリングする」のは`React.memo`の管轄外（防げない）。

### 「境界」で考える

`React.memo`/`useCallback`が効くのは、あくまで**親コンポーネントから子コンポーネントへpropsを渡す境界**でだけ。コンポーネントの内部で定義して、その内部の素のDOM要素（`<button>`の`onClick`など）にしか渡していない関数は、この境界を一度も越えないため、`useCallback`で包んでも意味を持たない。

### StrictModeでの2回描画

`src/main.tsx`の`<StrictMode>`は、開発モード限定でコンポーネントの描画関数をわざと2回呼び出す仕組み。副作用のバグ（本来1回しか実行してはいけない処理が紛れ込んでいないか）を見つけやすくするためのもので、バグではない。本番ビルド（`vp build`）では1回しか呼ばれない。再レンダリングを確認するときは「回数」ではなく「何が描画されたか」を見るとよい。

### 再レンダリングを確認する手順（console.logを使う簡易な方法）

1. 確認したいコンポーネントの関数本体の先頭に `console.log("コンポーネント名 render:", 識別できる値)` を一時的に追加する
2. `vp dev` を起動し、ブラウザのdevtoolsのConsoleタブを開く
3. 実際に操作して、コンソールに何が出るか観察する
4. 終わったら`console.log`は消す（コミットしない）

見るべきポイントは回数ではなく、**「操作していない要素まで描画されているか」**。例えばリストの1件だけを操作したのに、関係ない他の要素のログも出ていたら、そこに無駄な再レンダリングがある。

### 実例：TodoItemでの調査（STEP5）

コードレビューで、`TodoItem`内の`startEditing`/`cancelEditing`/`handleEditSubmit`（編集の開始・キャンセル・確定の関数）を`useCallback`化すべきか指摘された。上記の手順で実際に確認したところ：

- タスクの追加・チェック切替・削除（`App`の状態`todos`が変わる操作）→ 変更していない他のタスクまで再レンダリングされていた（`TodoItem`に`React.memo`が付いていないため）
- 編集ボタンを押す（`TodoItem`自身の`useState`（`isEditing`）が変わる操作）→ そのタスクだけが再レンダリングされていた

この結果から:

- `App.tsx`の`onToggle`/`onDelete`/`onEdit`が渡る先の`TodoItem`には`React.memo`を追加する価値がある（実際に無駄な再レンダリングが起きていたため）
- `startEditing`等は素のDOM要素にしか渡していない（「境界」を越えない）ため、`React.memo`を追加してもしなくても`useCallback`は効果がないと判断し、対応しないことにした

## データまわり

### データモデル

アプリが扱うデータを「どんな項目を持つ、どんな形」で表すか決めること。「タスク1件ってどんな情報を持つ？」を洗い出す。→ [docs/03-data-model.md](../docs/03-data-model.md)

### 型（type）

「このデータはこういう形」という説明書き。書いておくと `completed` に文字を入れる等の間違いを、書いている途中で気づける。バグを未然に防ぐ仕組み。

### なぜ id が必要？

同じ文字のタスクが2件あると文字だけでは区別できない。1件ずつにかぶらない目印（id）を付けておくと「操作されたのはどれか」を特定できる。`crypto.randomUUID()` で自動生成できる（世界でほぼかぶらないランダム文字列）。

### JSON

データを文字列として表す決まった書き方。localStorageは文字列しか保存できないので、`JSON.stringify`（データ→文字列）で保存し、`JSON.parse`（文字列→データ）で戻す。

### localStorage

ブラウザが持つ小さなデータ保存場所。再読み込みやブラウザを閉じても残る。ただしその人のそのブラウザ内だけ（別PC・別ブラウザには引き継がれない）。今フェーズの保存先。次フェーズでサーバー/DBに差し替える予定。

## コメントの書き方まわり

### コメントは「何を」ではなく「なぜ」を書く

コードを読めば分かること（例: `i = i + 1; // iに1を足す`）をそのまま日本語にしたコメントは、現場では嫌われる。価値があるのは、コードをいくら読んでも分からない **背景・意図・理由・ハマりどころ**（例: 「外部APIが稀にnullを返すのでここで空文字に寄せる」）。

### 自明なコメントは書かない

理由は2つ。①コードを直してコメントを直し忘れると、嘘の情報が残る（コメントは自動チェックされない）。②良い**命名**は最良のコメント＝ `d` ではなく `daysUntilExpiry` にすれば説明は要らない。TypeScriptでは**型**も説明の役割を持つ。「良い名前＋型」で自明にできるものはコメントを消す方向に倒すのが今の主流。

今回の `Todo` 型でも、`title: string`／`completed: boolean` は名前で自明なのでコメントを削除。`id` だけ「crypto.randomUUID() で採番する」という"どうやって"の情報を残した。→ [docs/03-data-model.md](../docs/03-data-model.md)

### JSDoc（`/** ... */`）

`//` と違い、**その型・関数を使う側**にエディタのホバーで説明が表示される書き方。普通のコメントは書いた場所でしか見えないが、JSDocは呼び出す場所から見えるのが強み。だから「他人（未来の自分含む）が使う部品」に書くと効く。

初心者のスタンス：全部に書くのを目指さず、①まず良い命名を頑張る → ②それでも伝わらない「なぜ・使い方の注意」をJSDocで補う、の順。`@param`／`@returns` は型を繰り返すだけならノイズになるので、**説明を足せるときだけ**書く。「JSDocを覚える」より「どこに情報が足りないかを見抜く」練習だと考えるとよい。効く場所は関数・カスタムフック（例: `useTodos` の使い方）や、理由の要る型フィールド。

## HTTP通信・DI（依存性注入）まわり

### DI（依存性注入）とは

コンポーネントや関数が「何かを使う」とき、その実体を自分の内部で作らず**外から渡してもらう**設計の考え方（Dependency Injection の略）。「外部との通信」のように差し替えたくなるもの（本番用の本物／テスト用の偽物）に向く。呼び出す側は「何ができるか（インターフェース＝約束事）」だけを知り、「実際にどうやるか」は知らないままにできる。

### 実例：`useTodos` が `fetch` を直接呼んでいた問題（STEP11のレビュー指摘）

STEP11で `useTodos.ts` を localStorage → SWR + `fetch` 呼び出しに置き換えたとき、最初は `fetch` をモジュール内で直接呼ぶ形にした。動くには動いたが、レビューで次を指摘された。

- テストが `fetch` をグローバルに乗っ取る（`vi.stubGlobal("fetch", ...)`）しかなくなる。すると「初期GET→操作→再取得GET」という**呼び出し順**までモックで再現する必要があり、SWRの内部実装が変わっただけで全テストが一斉に壊れる脆さを持つ
- グローバルな `fetch` を差し替えているので、後片付け（`vi.unstubAllGlobals()`）を1つのテストで忘れると、無関係な他のテストに影響が漏れて原因究明しづらい失敗を生む
- テストが「HTTPの細部（URL・メソッド・`Response`の組み立て・`Content-Type`）」を知りすぎている。本来書きたいのは「`addTodo`を呼んだら一覧が増える」という**振る舞い**だけ

これはモックの書き方の問題ではなく、**「通信の詳細」と「状態管理のロジック」を1つの関数に混ぜてしまった設計の問題**、というのがレビューの要点だった。「テストを書いていて辛いと感じたら、実装側の依存の持ち方を疑う」。

### 解決：`TodoApi` という約束事 + Reactの `context` で注入する

1. `src/front/api/todoApi.ts`：`TodoApi` という型（`fetchTodos`/`addTodo`/`updateTodo`/`deleteTodo`を持つ）と、実際に `fetch` を呼ぶ本物の実装 `todoApi` を定義
2. `src/front/api/TodoApiContext.ts`：`createContext` で「今使うべき `TodoApi` の実体」を注入する仕組みを用意。デフォルト値は本物の `todoApi`
3. `useTodos.ts`：`useContext(TodoApiContext)` で `api` を受け取り、`api.addTodo(...)` のように呼ぶだけにする。`fetch` という単語は `useTodos.ts` から消える
4. `src/front/api/todoApi.fake.ts`：テスト専用の偽物。メモリ上の配列を読み書きするだけで、実際の通信はしない

テストでは `<TodoApiContext.Provider value={createFakeApi(initialTodos)}>` で本物を偽物に差し替えるだけで済む。`useTodos` は本物か偽物かを知らないまま動く。これが **DI（依存性注入）**。→ [docs/06-backend-architecture.md](../docs/06-backend-architecture.md) §4

### 実例：`toggleTodo` のシグネチャ変更（レンダー中の `ref` 書き込み問題）

DI化の前段として、いったん `useRef` で「最新の `todos` 配列を覗く」形にして `useCallback` の依存を安定させようとしたが、これもレビューで指摘された。

**コンポーネント本体の実行中（レンダー中）に `ref.current` へ読み書きするのはReactのルール違反**。コンポーネントは「同じ入力なら同じ出力を返す純粋な関数」であるべきで、Reactが並行レンダリング（concurrent rendering。描画を途中で破棄してやり直すことがある仕組み）の都合で描画をやり直すとき、破棄された描画でも代入だけは実行されてしまい、意図しない副作用の原因になりうる。

対応：`toggleTodo(id: string)` → `toggleTodo(id: string, completed: boolean)` にシグネチャを変え、**呼び出し元（`TodoItem`）が既に知っている値をそのまま渡す**形にした。`TodoItem` は自分の `todo` をpropsで持っているので、次の値（`!todo.completed`）はその場で計算できる。「refで状態を覗き直す」より「呼び出し側が知っている値を引数で渡す」ほうがデータの流れが素直、というのが教訓。

### DI化のメリットまとめ

- `useTodos.test.tsx`／`App.test.tsx` の両方で `fetch` モックの重複がなくなり、「操作したら一覧に反映される」という振る舞いの検証に集中できる
- HTTPの細部（URL・メソッドが正しいか）の正しさは `todoApi.ts` 単体のテストか、既存の `test/worker/` の結合テストに任せられる（責任がきれいに分かれる）
- STEP12（読み込み中・エラー表示）でも、`fake` のメソッドを1つ失敗させるだけでエラーパスを再現できるようになる
